# Localization

How every site and app in the organization is localized. A project may add to this, not
work around it.

Two layers, two mechanisms: the **interface strings** (buttons, labels, messages) and the
**content** (long texts: articles, readings, descriptions).

## Locales

- A locale is a lowercase language code (`en`, `uk`, `de`). No regions until there is a
  real reason for one.
- Each project keeps **one registry** of its locales: the code, the native name, the date
  locale, and which one is the default. The default is `en`.
- **Fallback is always to the default locale**, never to another translation.

## Interface strings

- One JSON dictionary per locale, nested keys, `{name}` for parameters, plurals through
  `Intl.PluralRules`.
- Every locale has the same keys. A missing key shows the default locale's text.
- The user's choice is kept on the device. Order of detection: the saved choice, the
  browser language, the default.

## Content

- **One file per content unit, with every locale inside it** (`locales: { en: {…}, uk: {…} }`).
  A change to one language has the others next to it in the same file, so they are not
  forgotten. When the source text changes, every locale is checked in the same pull request.
- A locale's page exists **only if the locale is in the file and complete**. A locale that
  is present but missing a required field fails the build. A locale that is absent is not
  built, and no page is made for it.

## URLs

The locale belongs to the whole site, not to a page.

- **The real address of a page always has its locale prefix**, the default locale too:
  `/en/hexagrams/1`, `/uk/hexagrams/1`. The site is built on these addresses, and they do
  not change.
- **The default locale is also served without a prefix**: `/hexagrams/1`. That is a
  shortcut for whoever types it, not an address: its canonical link points at the real
  address, and nothing on the site links to it.
- Which locale is the default is one setting. Changing it changes what the shortcut shows
  and moves no real address.
- The prefix is one optional route parameter at the root of the routes, so every kind of
  page (the landing, the policy, the content) gets its locale from one place.
- The path after the prefix is the same in every locale: a stable key (a number, an id),
  not a translated slug. The alternates of a page are then the same path under another prefix.
- The language switcher is made of real links, always to the real address. For a page the
  other locale does not have, it points to that locale's root.
- One function builds the real address of a page for a locale. Links, the switcher, the
  canonical link, the alternates, the sitemap and the analytics path all use it.

## SEO, on every page

- A canonical URL: the page's real address in its locale, also on the default locale's
  unprefixed shortcut.
- `hreflang` links between all variants that exist, each pointing back, and `x-default`
  pointing to the default locale. They use the real addresses, so the unprefixed
  shortcut is not in them. A variant that is not built is not linked.
- `<html lang>`, `og:locale` and `og:locale:alternate`, and `inLanguage` in the structured data.
- A title and a description written for the locale, not carried over.
- The sitemap is generated by the build, lists the real addresses only, and lists the alternates.
- Analytics reports the real address, so a page is one page in the reports.
- No redirect by the browser's language: it hides pages from crawlers, and a static host
  cannot do it anyway. A site may offer the switch in a banner.

## Adding a locale

1. Add it to the project's registry, with the native name and the date locale.
2. Add the dictionary and translate the interface strings.
3. Add the locale to the content files it should have. What is not complete is not built.
4. Check the pages, the switcher and the alternates of a page in the new locale, and that
   the sitemap lists them.

## Status

This is being tried on one project first, on its content pages. The rest of the sites
adopt it, or change it, after that.

## Open

- The shared code (the translate function, the registry, the route helper) lives in each
  project now and goes into the shared kit once it is used by more than one.
- A library for the interface strings is not used; reconsider it when a project has more than
  three locales.
